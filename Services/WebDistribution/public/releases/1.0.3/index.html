相比 1.0.2，改进了什么？What changed since 1.0.2?

1. 断网恢复不再无限等待网络重置1. Bounded network reset waits

1.0.2：断网或切换网络时，内核重置可能长时间不返回，并拖住遥测和控制请求。1.0.3：把重置放入独立队列，最多等待三秒，超时后继续尝试恢复网络设置；同一时间只允许一个重置任务，避免阻塞任务堆积。In 1.0.2, a network reset could stall during an outage or network change and block telemetry and control requests. In 1.0.3, resets run on a separate queue with a three-second wait budget. Recovery then continues with network settings restoration, while only one reset remains in flight.

2. 网络扩展意外退出后自动尝试重连2. Automatic reconnect after unexpected provider exits

1.0.2：扩展被系统终止时，可能被当成普通断开，应用保持未连接，需要手动重新连接。1.0.3：区分意外退出与主动停止，在用户仍希望连接时自动尝试恢复；最多重试五次，各次等待一、三、八、二十、四十五秒，避免无休止重试。In 1.0.2, a provider terminated by the system could be treated as a normal disconnect, leaving the user to reconnect manually. In 1.0.3, unexpected exits are detected and retried while the user still wants a connection. Up to five retries use delays of 1, 3, 8, 20, and 45 seconds.

3. 自动重连尊重用户的主动断开3. Explicit disconnects cancel automatic reconnects

新增连接意图保护：点击断开后，待执行的自动重连会被取消；手动发起连接会重新开始重试计数，连接成功后也会重置计数。Connection intent is now tracked separately. Disconnect cancels pending retries; a manual connection or successful recovery resets the retry budget.

验证范围Validation coverage

  • 485 项单元测试通过；Developer ID 签名、应用与 DMG 公证和票据装订通过。485 unit tests passed. Developer ID signatures, app and DMG notarization, and stapled tickets were verified.
  • Tart macOS 26.6.1 中验证 1.0.2 覆盖升级、TUN 20/60 秒断网恢复、双引擎异常退出重连，以及主动断开后保持未连接。Tart macOS 26.6.1 checks covered upgrading from 1.0.2, TUN recovery after 20/60-second outages, reconnects after both providers exited unexpectedly, and remaining disconnected after a user stop.

已知限制Known limitations

  • 测试配置下 ipv6.google.com 的 HTTPS 连接失败，回滚 1.0.2 后同样复现；普通 Google、Cloudflare 和百度请求正常。原生 IPv6 尚未验证。HTTPS to ipv6.google.com failed with the test configuration and also failed after rollback to 1.0.2. Requests to regular Google, Cloudflare, and Baidu succeeded. Native IPv6 remains unverified.
  • 首次异常恢复约 48 秒，其中约 45 秒为状态处理延迟；后续 TUN、透明代理分别约 8 秒、7 秒恢复。The first recovery took about 48 seconds, including about 45 seconds of delayed status processing. Later TUN and transparent proxy recoveries took about 8 and 7 seconds.
  • 本轮未重现原热点切换卡死条件，未完成实际整机睡眠唤醒、全部协议矩阵或 24 小时稳定性验证。The original hotspot-switch hang was not reproduced. Actual system sleep/wake, the full protocol matrix, and a 24-hour stability run were not completed.
