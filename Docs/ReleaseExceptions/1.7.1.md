# v1.7.1 发布验收说明

2026-10-12，修复版本，正式构建 2026101204。修复两个问题：透明代理切换到另一块网卡后不能自动恢复（只能手动重连）；规则页布局死循环导致 App 崩溃。引擎更新到核心 `20143a5`。分析与实施记录见 `Docs/Plan-1.7.1.zh-CN.md`。

## 变更内容

- **切换网卡自动恢复**
  - 核心 `20143a5`：新增 `clash_flow_engine_reset_network_state_v1`，把 flow 引擎的出站连接切到给定的物理网卡（0 表示由引擎选择），关闭上游连接并重置 DNS 客户端，2 秒上限，同一时间只允许一次重置。Flow ABI V8，数量门禁 26 → 27。
  - 透明代理扩展：物理网卡编号或地址签名变化时重置引擎；同一轮恢复的第 3 次尝试仍不通时，原地重建引擎，保留运行中改过的节点选择与路由模式；尝试用尽且有网卡时再重建一次。
  - App：网络变化或唤醒后 180 秒内，原本可用的线路失效时自动重连一次，10 分钟冷却。
  - 健康判定：TUN 与透明代理都不再把"收到下行字节"当作已恢复，只认经引擎的探测，先 GLOBAL 后 DIRECT。
- **规则页崩溃**：页面最外层由 `LazyVStack` 改为 `VStack`，规则列表本身仍是懒加载。
- **发布门禁**：新增 `scripts/test_interface_switch_recovery.sh` 与 `scripts/test_remote_interface_switch.sh`，写入 AGENTS.md 第 3 步，每次发布 TUN 与透明代理各跑一次。

## 验证结论

1. **本地回归**：`test_network_switch_gate.py`、`Tests/EngineReconnect/run.sh`、`Tests/RuntimeEnvironment/run.sh`、`./scripts/test.sh` 在最终代码上全部通过。新增单元测试覆盖引擎重置（Rust 与 FFI）、桥接状态映射、原地重建（含重建期间停止）、自动重连判定与探测顺序。
2. **12 协议真实互通（核心 `20143a5`）**：五组全部 PASS（48 个用例、26 次证书拒绝），日志在 `outputs/interop-20261012T034227Z/`。`verify_protocol_matrix.sh` 通过，含参考互通二进制校验。
3. **切换网卡（Mac mini，Ethernet en0 ↔ Wi-Fi en1）**：
   - 1.7.0 透明代理：关掉 Ethernet 后 15 秒内未恢复，判定 FAIL（复现了用户遇到的故障）。
   - 1.7.1 正式构建 2026101204：透明代理 6/6 次在 2–3 秒内恢复，TUN 6/6 次在 1–2 秒内恢复。日志显示每次路径变化后约 0.5 秒完成引擎重置，未触发重建。结果在 `outputs/interface-switch-1.7.1-2026101204-*.txt`。
4. **Tart VM 六维矩阵（macos27，QA 构建 2026101204）**：六个组合全部通过（空闲复用、SNI 恢复、2 MiB 上传），清理无残留。报告在 `outputs/vm-acceptance-1.7.1-2026101204/`。上传耗时见例外 4。
5. **Mac mini 远程门禁**：通过，证据在 `outputs/test-evidence/remote-arm64-20261012T084059Z-fast/`。
6. **Mac mini 真机（公证正式构建 2026101204）**：透明代理与 TUN 下空闲 50 秒复用、2 MiB 上传（5.4 秒 / 5.6 秒）全部通过，实际占用 65 MB / 64 MB。完成后恢复为透明代理模式。修复后 Mac mini 上没有新的崩溃报告。
7. **UI 性能与内存门禁**（Mac mini，Release，实时遥测，两档各 5 分钟）：
   - 展示档：切页 p95 127.3 ms、最慢 166.0 ms；内存中位数 63 MB、峰值 65 MB、增长 +0 MB。

   - 较 1.7.0：内存中位数 −3～−4 MB（66 → 62–63 MB）；规则页 p50 +18 ms（76 → 94 ms，分区不再懒加载），仍远在预算内（p95 ≤ 180 ms），预算未放宽。

8. **公证**：候选包 App 与 DMG 均 Accepted（提交 `4660f09f-cb2e-430f-a8a2-8829a4b859c2`、`56bb69db-e58b-4ce0-b2a5-7182f47401b5`），发布通道 `stable`。正式 DMG 打包时 App 与 DMG 再次提交，均 accepted 并完成票据装订；SHA-256 `425dea8b6bd901d31ef16e265b22684a618a25619685f0a184df1ced9646b0d2`。

## 例外说明

1. **UI 性能门禁首次失败，由此发现规则页崩溃**：最初两次运行每档只采到 2 次切页。审查版 App 在进入规则页约 30 秒后崩溃（"Update Constraints in Window 次数超过视图数"）。用同一门禁复跑 v1.7.0 源码同样崩溃，说明不是本次网卡修复引入的；本机也能复现。
   - 定位过程：自动切页逐对二分，问题只在规则页 → 静态打开规则页同样崩溃 → 断点确认循环发生在分栏的详情列 → 截图显示规则页内容比栏宽，滑到侧边栏下面 → 最外层改为 VStack 后布局正确、不再崩溃。
   - 经用户决定"先修崩溃再一起发布"，修复后门禁完整通过（见验证结论 7）。
   - 1.7.0 昨天能通过、今天必现的原因没有查清。系统版本未变（26A434），配置与夹具数据也不依赖日期。修复去掉了循环本身，不依赖这个触发条件。
2. **远程门禁的网络变更扫描**：门禁会拒绝 `scripts/` 下任何以 `networksetup -set…` 开头的行。新的切换网卡门禁有意关闭网络服务，第一次远程门禁因此失败。修复方式是只对这一个文件放行（`--exclude=test_interface_switch_recovery.sh`），并写明原因：门禁从不运行它，其余脚本照旧检查。没有改写命令来绕过扫描。
3. **候选包重建**：
   - 2026101201、2026101202 是开发期间装到 Mac mini 上验证修复的测试包。
   - 2026101203 是第一版正式候选，完成了全部门禁，只有 UI 性能门禁因规则页崩溃未过。
   - 修复后以 2026101204 重新构建，并重跑 `test.sh`、VM 矩阵、远程门禁、真机检查与 UI 性能门禁。
   - 2026101204 的公证候选连续两次在最后一步报"构建期间系统网络状态变化"：第一次是本会话并行跑 VM 矩阵启停了虚拟机；第二次是本机另一程序（ChatGPT 的 Codex CLI）在构建中途启动了同一台 `macos27` 虚拟机。没有干预该程序，在虚拟机持续运行期间第三次构建通过，前后网卡列表一致。
4. **VM 矩阵上传耗时**：经代理的 2 MiB 上传为 7.2–33.4 秒，最慢的组合每次不同（2026101203 时是 TUN/rule 25.9 秒，2026101204 时是 TUN/global 33.4 秒），同一引擎的其他组合约 7 秒。判定为虚拟机网络波动，与本版本无关。Mac mini 真机两种模式都是 5.4–5.6 秒。
5. **未跑 VM UI 测试套件**：该套件不在 AGENTS.md 规定的发布门禁内（1.7.0 额外跑过）。本次 UI 只改了规则页的外层容器，`macos27` 当时被另一程序占用。规则页在 UI 性能门禁里两档共切入 138 次，并截图核对了布局。
