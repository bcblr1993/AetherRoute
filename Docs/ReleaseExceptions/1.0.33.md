# v1.0.33 发布验收说明

2026-09-29，修复透明代理模式下 Chrome 等自带 DNS 解析的应用无法访问 Google 的问题，新增透明代理 SNI 目标恢复发版门禁，虚拟机矩阵与真机门禁改为并行执行。

### 修复

1. **透明代理按 ClientHello 域名转发（`Core/Engine` Dispatcher）**：
   - Chrome 使用自带 DNS 解析器，或应用直接连接 IP 时，macOS 交给透明代理的只有 IP、没有域名。遇到 DNS 污染时这个 IP 属于无关服务器（例如 `www.google.com` 被解析为 Facebook 的地址），引擎按 IP 转发，连接挂起，表现为 Chrome 打不开 Google，而 curl、Safari 等通过系统解析的应用正常；
   - 透明代理的 443 端口 IP 目标现在会读取 TLS SNI（与 TUN 的 Fake-IP 恢复一致），按域名匹配规则并转发；读不到 ClientHello 时在 500 ms 后退回按 IP 转发。TUN 模式行为不变。

### 新增

2. **透明代理 SNI 目标恢复门禁（`scripts/test_transparent_sni_recovery.sh`）**：
   - 用 `curl --connect-to` 把 `www.apple.com` 故意拨到无关 IP（`1.1.1.1`），必须通过 `www.apple.com` 的证书校验；已纳入虚拟机矩阵的三个透明代理组合，TUN 组合记为跳过。

### 流程

3. **发版验证并行化**：Tart 虚拟机 6 维矩阵与物理真机门禁同时执行。

### 验证结论

1. **本地回归**：`test_network_switch_gate.py` 3/3、`Tests/EngineReconnect/run.sh`、`Tests/RuntimeEnvironment/run.sh`、`./scripts/test.sh` 全部通过；引擎单元测试 341 通过、0 失败；运行时验收回归 37 个用例通过。
2. **Tart 虚拟机矩阵（`macos27`）**：6 个组合全部通过，6 个组合的空闲 Keep-Alive 复用与 3 个透明代理组合的 SNI 恢复检查均通过。首轮 `tun/direct` 的 captive portal 探测因虚拟机直连 Cloudflare 网络波动超时一次（未开 AetherRoute 时直连也需 1.4 s），单独重跑通过。测试后已清理虚拟机临时文件。
3. **物理真机（Apple Silicon Mac mini）**：`test_remote_arm64.sh fast` 通过。使用公证候选包：透明代理模式 SNI 恢复通过（1.0.32 失败）、Chrome 正常打开 Google 与 YouTube（1.0.32 为 0 字节）、空闲复用通过；TUN 模式空闲复用通过、Chrome 正常打开 Google。
4. **协议矩阵与许可证**：`verify_protocol_matrix.sh`、`verify_licenses.sh source` 通过，正式核心哈希与 `Config/ProtocolCoreEvidence.json` 一致。
