## 例外

### 1. httpbin.org 拒收大请求体，上传门禁改用 Cloudflare

并行验收首轮（`outputs/acceptance-1.9.1-2026102801`）6 个组合（包括两个 `direct`）都只在大上传一项失败：`HTTP 400 after 65394 of 2097152 bytes`。不经代理，直接从本机访问也得到同样的结果，响应体为 `http: request body too large`，60 KB 的请求则正常。所以原因是 httpbin.org 不再接受超过约 64 KiB 的请求体，与代理无关。go-httpbin 的几个镜像上限都在 1 MiB 左右，postman-echo 与 beeceptor 也不行。

`scripts/test_large_upload.sh` 的默认端点改为 `https://speed.cloudflare.com/__up`，判定条件是 HTTP 200，并且响应头 `cf-meta-upload-bytes` 等于发送的字节数。请求是端到端 HTTPS，代理改动或截断任何字节都会让 TLS 记录校验失败，不可能得到 200；字节数由服务端统计，不依赖 curl 自己的写入计数。原有的 httpbin 回显逐字节比对保留，可用 `AETHERROUTE_LARGE_UPLOAD_URL` 切回。`test_large_upload_gate.py` 新增"计数一致 / 计数少 1 / 缺少计数头"3 项对照，共 13 项全部通过。物理机证据仍要求至少送达 2 MiB，标准没有放宽。

### 2. VM 矩阵使用 QA 构建号 2026102803

第 2 轮并行验收的 QA 包与首轮同为构建号 2026102801。VM 的 sysextd 没有替换已激活的同版本扩展，矩阵报 `tunnel PID … does not match the installed candidate`，之后又报退出校验超时（与 1.4.1 时的情况相同）。重启 VM 后改用构建号 2026102803 单独构建 QA 包（`AETHERROUTE_QA_AUTOMATION=1`、Normal Core），矩阵全部通过。

中间那次 2026102802 漏了 QA 自动化开关，被矩阵拒绝，没有执行任何检查。三个 QA 包与正式构建 2026102801 来自同一份源码，区别只在构建号和 QA 自动化开关。远程 ARM64 与 UI 性能门禁在第 2 轮正常完成。
